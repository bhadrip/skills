# Voice profile

Read this when learning a voice, resolving a mismatch, or saving or updating a profile. Work from authentic samples and targeted elicitation. Start with a representative sample for the task at hand and ask for more as needed.

## Record the formula

A style rule has **scope + situation that triggers it + observable choice + evidence + status**. Scope can name a language, channel, audience relationship, or kind of message. Include only dimensions that affect how the person writes.

| Status | Meaning | Use |
| --- | --- | --- |
| Confirmed | The user stated or confirmed the rule and its scope | Apply within that scope |
| Observed | The same choice recurs in independent examples in comparable settings | Apply as a tendency within the observed scope |
| Tentative | One example or a scope that needs checking | Ask when it would affect the draft. Match an example for the current draft when the user chooses it as a model |
| Unknown | No applicable evidence | Leave the rule unset. Ask when the draft depends on it |

During calibration, use short labels to track which session examples or instructions support a rule. For long-term use, translate supported tendencies into the predefined labels in [local profile storage](local-profile.md). Persist only the generic scope, observed or confirmed status, feature, and choice. Omit a trait when there is no suitable label. Keep exact wording and evidence references transient, and use new fictional scenarios to illustrate the resulting style.

## What to look for

| Dimension | Observable choices |
| --- | --- |
| Opening and order | Ask or answer first, context first, greeting, setup, where the reason goes, and whether they recap or end with a next step |
| Information and explanation | Amount of context, details left implicit, how they use examples, how they link reasons to actions, and how much they repeat |
| Words and phrases | Contractions, idioms, everyday or technical words, favorite transitions and request phrases, and deliberate language switching |
| Grammar and rhythm | Fragments or full sentences, sentence length, clause patterns, questions, pronouns, and the rhythm of short and long lines |
| Stance and relationship | How they request, decline, disagree, apologize, acknowledge, joke, hedge, or express certainty, and what they change with familiarity or stakes |
| Presentation and interaction | Case, punctuation, line breaks, bullets, emoji, greeting, sign-off, message length, and whether a reply echoes the question or gets straight to the answer |

During the current task, notice patterns the user endorses for opening a request, explaining a delay, declining, disagreeing, or following up. An observed “could you” pattern can become the predefined request-form label `could_you`. Working examples use fictional details and entirely new sentences. Let unsupported slots stay empty.

## Elicit the missing choice

Ask for production before adjectives. Use one small scenario close to the actual message. Request the exact wording, including punctuation or line breaks if they matter. Label any variants you propose as prompts for feedback and record preferences only once the user confirms them.

- **Slack request.** “A teammate hasn’t replied about a review you need today. What would you send them?”
- **WhatsApp logistics.** “You’re running 15 minutes late to meet a friend. What would you text them?”
- **Email update.** “You need to tell a client their delivery is moving by two days. How would you open the email and ask them to confirm the new date?”
- **Check transfer.** “In your Slack examples, you put the ask first. How would you open this same request in an email to a client?”

If the same feature varies, look for a condition that explains the difference, such as an existing thread or the recipient’s familiarity. Ask whether the condition matters when the examples alone leave it unclear. If the user says “that’s better,” use the correction in the current task. Ask a focused scope question if you need to turn that approval into a standing rule.

## Worked example with fictional evidence

- **E1, Slack to a teammate.** “can you check the numbers by 2? need them for the review”
- **E2, Slack to a teammate.** “can you send me the screenshots today? need them for the doc”

For routine Slack requests to teammates, these samples support three observed tendencies. Lead with “can you,” put the timing inside the request, and follow with a short reason. Lowercase also recurs in both messages. Client email openings and emoji preferences remain unknown.

The new Slack brief asks Taylor to leave feedback by Wednesday so the user can finalize the deck Thursday. A draft supported by these samples is “can you leave feedback by wednesday? need it to finalize the deck thursday”. The facts come from the new brief. The shape comes from the samples. If the same brief is for a client email and those are the only samples, ask for a short email example or the user's opening line.
